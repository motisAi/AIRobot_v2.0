# Stella — Architecture & Roadmap (2026-09-13)

_Produced by a multi-agent audit + research + design pass (16 analysis agents, cited). This is the canonical plan; implement phase by phase, rollback-safe._

## North Star

Stella is a self-learning Pi5 + Hailo-10H robot that is NEVER deaf, NEVER dead, and ALWAYS degrades gracefully. Every capability has an online primary AND a CPU-only offline fallback that needs no internet and no HailoRT upgrade, so a dead cloud, a rate-limited provider, a flaky USB mic, or an un-upgraded NPU all degrade her to slower-but-working, never to silent or dangerous. Two structural cures anchor the design: (1) ONE dispatch/auth spine that both voice-keyword handlers and LLM tools call, so master-auth is checked exactly once (closing the bypass) and the same tool set is exposed online and offline (closing the capability cliff) — today every capability is implemented twice with no shared source of truth, which is the direct root of BOTH bugs (audit notes, top_problems). (2) The Hailo NPU is a BONUS tier, treated as optional/late: no reliability guarantee depends on the invasive 5.1.1->5.2.0 DKMS driver rebuild. Perception is layered and event-driven — a cheap always-on CPU/NPU object detector decides WHEN to spend an expensive on-demand VLM call; nothing in the routine loop touches the network. Free-only assets: Groq (LLM+Whisper), NVIDIA NIM (existing nvapi- key: LLM/VLM/embeddings), Moondream (VLM), Gemini (tertiary), and the local stack (openWakeWord, faster-whisper, ollama-CPU, Piper, dlib, Hailo). Every change is small, git-committed before deploy, and revertible via a config flag or single-file revert.

## Why object recognition doesn't work (root cause)

Object recognition is DEAD at runtime, with three independent blockers hit in this order. The one the running service actually trips on is #1.

BLOCKER 1 (what the live service actually hits) — NO MODEL FILE OF ANY KIND. config sets object_model='yolov8n', so the NPU branch needs data/models/yolov8n.hef and the CPU-DNN fallback needs data/models/yolov8n.onnx (or MobileNetSSD_deploy.prototxt+.caffemodel). Live `find ~/AIRobot_v2.0/data/models` shows ONLY piper/ (TTS) and vosk-small-en/ (STT) — no .hef, no .onnx, no caffe anywhere (`sudo find / -name '*.hef'` returns only hailo-ollama's content-addressed LLM blobs). So HailoDetector.start() (hailo_detector.py:105+) logs 'No DNN model found' -> 'Object detection off — no model present' and RETURNS FALSE. ObjectDetectionModule.start() (object_detection.py:80-82) returns BEFORE it ever calls camera_manager.subscribe(), so 'object_detection' is not in the camera subscriber list (live list = motion_guard, web_dashboard, face_recognition), _on_frame never runs, and get_current_objects() is always []. Crucially the OpenCV-DNN CPU branch runs regardless of enable_hailo/NPU, so even the free CPU fallback is dead purely for lack of a file. This is the single lowest-effort fix: drop a YOLOv8 yolov8n.onnx into data/models/ (postprocess _postprocess_yolo_onnx already targets that export layout) and CPU detection comes alive with no config change.

BLOCKER 2 (would block the NPU path even with a model) — enable_hailo is intentionally FALSE. The loaded config is config/config.yaml (settings.py:35 default_config_path; the repo-root /config.yaml is a stale 'Gonzo' duplicate with enable_hailo:true that is NEVER loaded). config/config.yaml:228 system.enable_hailo:false with comment 'leave the Hailo NPU for hailo-ollama'. So hailo_detector.py:105 `if system_config.enable_hailo and HAILO_AVAILABLE:` is False and _init_hailo() is skipped entirely (matching the live log showing no Hailo attempt, straight to the DNN fallback).

BLOCKER 3 (would block the NPU path even if enable_hailo were true) — the Python Hailo bindings cannot import. venv has pip hailort==4.23.0 whose _pyhailort is ABI-linked to libhailort.so.4.23.0, but the system runtime is HailoRT 5.1.1 (only /usr/lib/libhailort.so.5.1.1 exists). `venv/bin/python -c 'import hailo_platform'` -> ImportError: libhailort.so.4.23.0: cannot open shared object file. So HAILO_AVAILABLE=False (hailo_detector.py:46-47). requirements.txt:45-47 says hailort must NOT be pip-installed — the 4.23.0 wheel is an erroneous install. Even after fixing the import, hailo_detector.py's _init_hailo/_detect_hailo are written to the HailoRT 4.x API (ConfigureParams.create_from_hef, InferVStreams) while the runtime is 5.x, and _postprocess_yolo assumes a raw [x,y,w,h,obj,cls...] tensor whereas model-zoo YOLOv8 HEFs usually embed NMS — so NPU enablement needs a matched 5.1.1-DFC/HAILO10H .hef, a HailoRT-5.1.1 pyhailort wheel from the h10-hailort bundle (not PyPI), enable_hailo:true, AND code porting.

NET: it is NOT one cause. The proximate runtime cause is a missing model file (kills even the CPU fallback); the NPU path is additionally gated off by config and broken by a 4.x-vs-5.1.1 SDK/firmware mismatch plus 4.x-era code. NOTE the misleading signal: settings.py detect_hailo_device() returns True just because /dev/hailo0 exists (checked before the import), so system HAILO_AVAILABLE=True — but the real gate is hailo_detector.py's import-based HAILO_AVAILABLE, which is False.

## Reliability & security design

MIC-HANG (HIGHEST severity, top_problems #1): the blocking PortAudio stream.read() at speech_recognition.py:175 can hang forever on a stalled USB mic, freezing the conversation loop until the watchdog does a full restart that wipes guard/session state. The safe reader-thread fix was reverted because a cross-thread stream.close() caused heap corruption (malloc_consolidate SIGABRT). REAL FIX, two-tier: (a) interim rollback-safe step behind a capture_timeout_enabled flag — add a wall-clock deadline independent of frame arrival and, on stall, reopen a FRESH PyAudio stream ON THE SAME reader thread (NEVER close a stream cross-thread); an overall capture deadline returns None and re-arms the wake mic in-process without a restart. (b) fuller fix — migrate capture to a sounddevice callback model with a bounded queue on an EXPLICIT ALSA device index, VAD-chunked, so the callback never blocks the loop and there is no cross-thread close. Only true in-process recovery closes this loop.

MIC ENUMERATION FLIP-FLOP (top_problems: PortAudio only lists mics free at probe time): pin mics by stable ALSA hw: identifier (card by USB path), not by flaky PortAudio name; fail LOUD (log ERROR + retry) when the wake mic resolves to None instead of silently opening 'default' (pulse->USB), which collapses both roles onto the one USB command mic (wake_word.py:206). Wire the unused AudioManager exclusive-lease API.

WAKE WORD: replace the Vosk alias/Levenshtein string-matcher (wake_word.py:294/317) with a trained openWakeWord 'Hey Stella' CPU model, VAD-gated, threshold tuned; keep Vosk as a corroborating second detector that only fires with VAD/energy — this kills both missed wakes and taylor/sailor/settler false wakes.

WATCHDOG (top_problems: hard-restarts mid-conversation): threshold is 60s in code vs 120s in the docstring, and _conv_activity is stamped ONLY when Stella speaks — so a long user pause or a ~20s slow-provider/NPU round-trip trips a full 'sudo systemctl restart airobot'. Fix: raise 60s->120s (watchdog.py:63), stamp _conv_activity on USER speech AND on LLM request start AND finish (manager.py), and prefer an in-process session-abort flag over the full service restart so guard/session state survives.

MASTER-AUTH BYPASS (top_problems, security): the deterministic keyword handlers (_maybe_ac at manager.py:859, _maybe_music/_maybe_mirror/_maybe_face, guard-arm) run FIRST, short-circuit before think(), and perform NO master check — while the equivalent LLM tools (set_ac/control_device/set_guard_mode at manager.py:418-439) DO. Any present speaker (even 'unknown, no recent face') can control AC/music/screen/hand and ARM guard by phrasing it as a keyword. FIX: single source of truth — extract one _require_master() helper (getattr(brain,'master_mode',False) or getattr(robot,'_remote_master',False)) called at the top of every mutating handler; longer-term route every capability call (keyword AND tool) through ONE dispatch layer that checks auth exactly once, and unify _do_device_control vs control_device _remote_master handling.

OFFLINE RESILIENCE / CLIFF (top_problems): gate web/weather pre-injection on whether a cloud client actually ANSWERED, not on a client merely existing (ai_engine.py:429-434) — today web context is skipped whenever an OpenAI client exists even if it then fails to the NPU. Add NIM as an independent cloud fallback (fail over on 429/empty-content, not just network loss). Add the _TEXT_TOOLCALL_RE tool-call shim so the offline qwen brain keeps device/guard/music/reminder tools instead of collapsing to plain chat (ai_engine.py:504-506). Every capability row above has a CPU-only offline path needing no NPU, so a failed HailoRT upgrade or a dead internet degrades Stella to slower-but-working, never deaf/dead.

SECURITY HYGIENE (top_problems, medium): rotate ALL exposed live plaintext keys in the review snapshot (.env GROQ/GEMINI/MOONDREAM/TELEGRAM/SENSIBO, tinytuya.json apiKey/apiSecret, devices.json local key — working keys, not placeholders); gitignore .env/tinytuya.json/devices.json; move to a systemd EnvironmentFile with 600 perms; ensure future review snapshots exclude them. Queue Telegram alerts offline and flush on reconnect rather than dropping them silently. Delete the stale repo-root /config.yaml (Gonzo, enable_hailo:true, NEVER loaded — the live file is config/config.yaml, Stella) to stop silent mis-edits.

## Roadmap (phased, rollback-safe)

### Phase 0 — Stop the bleeding (reliability + security, no new models, no NPU) — Close the five recurring reliability/security pains with the smallest reversible changes so Stella stops going deaf/dead and stops obeying the wrong person. Nothing here touches the NPU or downloads a model.
_effort: medium · risk: medium — the mic-hang fix touches audio threading that has crashed before; mitigate by same-thread-only stream ops, a feature flag defaulting to the proven path, and testing on the Pi before enabling. Auth/watchdog/enumeration/secret changes are low-risk single-function edits. · depends: Nothing. All CPU-only, no NPU, no new downloads. Git hygiene is the only prerequisite, done first in this phase._

- Git-commit the current working tree FIRST as a baseline to revert to (confirm the motisAi/AIRobot_v2.0 remote is current); confirm config/config.yaml is the loaded file (settings.py:35), NOT the stale root config.yaml.
- MASTER-AUTH: extract one _require_master() helper and call it at the top of every mutating keyword handler — _maybe_ac (manager.py:859), _maybe_music, _maybe_mirror, _maybe_face, and guard ARMING — mirroring the check already in set_ac/control_device (manager.py:418-439).
- MIC-HANG (behind capture_timeout_enabled flag, default the proven path): add a wall-clock deadline to the capture read loop (speech_recognition.py:175) and reopen a FRESH PyAudio stream ON THE SAME reader thread on stall; overall deadline returns None and re-arms the wake mic in-process (NEVER close a stream cross-thread — that caused the SIGABRT revert).
- MIC ENUMERATION: pin mics by stable ALSA hw: identifier; when the wake mic resolves to None, log ERROR + retry instead of silently opening 'default' (wake_word.py:206).
- WATCHDOG: raise 60s->120s (watchdog.py:63), stamp _conv_activity on user speech and LLM request start/finish, and prefer an in-process session-abort over 'sudo systemctl restart airobot'.
- SECRETS: rotate all exposed live keys (GROQ/GEMINI/MOONDREAM/TELEGRAM/SENSIBO, Tuya apiKey/apiSecret, Tuya local key); gitignore .env/tinytuya.json/devices.json; move to a systemd EnvironmentFile with 600 perms.
- CONFIG HYGIENE: delete the stale repo-root /config.yaml (Gonzo) and dead duplicate modules to prevent silent mis-edits.

**Rollback:** Each item is an independent git commit behind a config flag or single-file revert; the mic-hang fix ships disabled behind capture_timeout_enabled and flips off instantly. Every change committed and smoke-tested before 'systemctl restart airobot'.

### Phase 1 — Revive dead & fragile perception + offline voice (CPU only, no NPU) — Bring object detection back to life and make the wake word and offline STT actually reliable — all on CPU, no HailoRT upgrade. This is the #1 daily-experience win.
_effort: medium · risk: low — additive, each behind a flag; the .onnx drop is trivially reversible (delete the file). openWakeWord runs beside Vosk so a bad model is a one-line flip back. CPU engines compete for cycles — keep to base models and VAD-gate. · depends: Phase 0 mic-capture/VAD fix (so faster-whisper/openWakeWord don't inherit the same hang)._

- OBJECT DETECTION: drop data/models/yolov8n.onnx onto the Pi (CPU OpenCV-DNN branch; _postprocess_yolo_onnx already matches that export). No config change, enable_hailo stays false. Verify object_detection subscribes to the camera and emits object_detected events.
- WAKE WORD: train an openWakeWord 'Hey Stella' model in the free Colab (synthetic voices + 10-30 real recordings), deploy CPU-side, VAD-gate, tune threshold. Run alongside Vosk behind a wake_engine flag; require VAD/energy corroboration for Vosk wakes.
- OFFLINE STT: install faster-whisper base.en (int8) and wire it as the offline transcription fallback ahead of Vosk; add Moonshine base.en for short commands. Demote Vosk to last-resort.
- FACE RECOGNITION: switch face_backend opencv->dlib HOG for aligned crops, report raw distance, remove the double frame-skip (camera + module). Pure code changes, existing embeddings DB reused.
- Regenerate a pinned requirements.txt from the working venv (add paho-mqtt/tinytuya/mediapipe/opencv-contrib/yt-dlp; EXCLUDE system hailort) so a clean install doesn't silently disable live features; update check_deps.py.

**Rollback:** Delete yolov8n.onnx; set wake_engine: vosk; set STT offline fallback back to vosk; revert face_backend to opencv — each a single config line or file removal.

### Phase 2 — Close the online/offline cliff + add NVIDIA NIM (one key, three wins) — Make the brain degrade gracefully: an independent cloud fallback path, a free strong online VLM and embeddings, and a tool-capable offline brain so device/guard/music/reminders keep working with no internet — all on assets already held.
_effort: medium · risk: low-medium — NIM is near-zero-effort (one key, one URL) but cloud-only, 40 RPM ceiling, prototyping-license (fine for a home robot, not a sold product), and versions model IDs frequently (verify in the Build console). Offline tool-calling on a 1.5B model is experimental — keep tool-heavy turns on the online tiers when connected. · depends: Phase 0 auth gate (dispatch unification reuses it); existing provider abstraction + nvapi- key. Independent of Hailo._

- Add NVIDIA NIM as one more OpenAI-compatible provider in ai_engine.py _clients + fallback_order (base URL https://integrate.api.nvidia.com/v1, existing nvapi- key): LLM secondary (Nemotron-3 / llama-3.3-70b), online VLM (llama-3.2-11b-vision), and RAG embeddings (llama-3.2-nv-embedqa-1b-v2). Throttle to <40 RPM; cache; never per-frame. Route failover on 429/timeout, not just no-network.
- FIX WEB GATING: gate web/weather pre-injection on whether a cloud client actually ANSWERED, not on a client merely existing (ai_engine.py:429-434).
- OFFLINE TOOLS: deploy ollama qwen2.5:1.5b-instruct on the Pi5 CPU (native tool calling) as the offline brain, and add the text tool-call shim using _TEXT_TOOLCALL_RE (ai_engine.py:599) so the offline backend can drive device/guard/music/reminder tools.
- UNIFY DISPATCH: route keyword handlers and LLM tools through one capability-dispatch layer with the single master gate from Phase 0, so online and offline paths expose the same tools with the same auth.
- MEMORY INDEX: stand up a local RAG index (SQLite/FAISS) wired to _recall_context; enforce input_type query-vs-passage and one-embedder-per-index (NIM online-only index, local sentence-transformer for the persistent/offline index).

**Rollback:** NIM is a chain entry — remove it from the provider list to revert. ollama/memory index are additive (delete the index file, disable the flag). Web-gating and dispatch-unify changes are single-function edits behind commits.

### Phase 3 — Offline vision insurance (CPU) — Give scene-understanding an offline path so 'what am I holding' still answers with no internet, without waiting on the NPU.
_effort: medium · risk: low — additive CPU services behind an interface; heavy CPU load mitigated by on-demand-only invocation. · depends: Phase 2 (NIM VLM + provider abstraction). Independent of Hailo._

- Stand up Moondream Photon/Station on the Pi5 CPU as the offline VLM fallback (base-URL swap from Moondream Cloud); accept multi-second latency as the degraded offline mode.
- Put all VLM engines behind one interface: Moondream Cloud -> NIM 11B-vision -> Moondream Photon(CPU). Fire only on demand or on a detector event (unknown object), never per-frame; downscale to ~1024px JPEG before any cloud call.
- Wire the object detector's cheap 'there is an object, class X' as the gate that decides WHEN to spend the expensive VLM 'what exactly is this' call.

**Rollback:** Remove Photon from the VLM interface chain; the cloud paths are unchanged.

### Phase 4 — OPTIONAL / LATE / ISOLATED: HailoRT 5.1.1 -> 5.2.0+ upgrade — Only after the CPU offline stack is proven and committed, clear the single version gate blocking all pyhailort inference. Explicitly deferred and isolated because it is invasive and NOT required for any reliability guarantee.
_effort: medium · risk: high — invasive DKMS kernel-driver rebuild can break other Hailo apps/pipelines pinned to 5.1.1; version-gate re-triggers HAILO_NOT_IMPLEMENTED if any component drifts. Custom HEFs need the x86 Dataflow Compiler + >=1024 calibration images. · depends: Phases 0-3 complete (CPU offline stack proven, providing the safety net that makes this upgrade reversible). Nothing else technically blocks it, but lower-risk/higher-impact work goes first. Enables Phase 5._

- Take a full system/image backup and note pinned versions; do this in a maintenance window on a branch/snapshot, not the live main deploy (this rebuilds the PCIe kernel driver via DKMS and can break apps pinned to 5.1.1).
- pip uninstall the erroneous hailort 4.23.0 wheel (it ABI-mismatches the 5.1.1 runtime and violates requirements.txt).
- Ubuntu Server 24.04: do NOT 'apt install hailo-all' (that is Raspberry-Pi-OS only). Install deps (bison flex libelf-dev dkms), remove old h10-hailort* packages, dpkg -i the Developer-Zone .debs at ONE matched version >=5.2.0 (target 5.3.0 for Qwen3-VL): hailort, hailort-pcie-driver, hailo_gen_ai_model_zoo, hailo-tappas-core; reboot; verify 'hailortcli fw-control identify'.
- Install the matching HailoRT-5.2.0 aarch64/cp312 pyhailort wheel from the bundle (NOT PyPI); verify 'import hailo_platform'. Keep runtime + firmware + PCIe driver + DFC + model-zoo tag all on ONE major line or you re-trigger HAILO_NOT_IMPLEMENTED.

**Rollback:** Hold the pre-upgrade system image; if the driver/firmware breaks, restore the image and stay on 5.1.1. Because every capability already has a proven CPU offline path from Phases 1-3, a failed upgrade degrades to Phase-3 state, not a dead robot.

### Phase 5 — On-NPU perception + offline brain/vision (after 5.2.0+) — Move perception onto the NPU (frees the CPU, cuts power to ~2W) and complete a 100%-offline brain+vision loop. Every model here is a toggle over the working CPU path, never a dependency.
_effort: medium · risk: medium — single NPU context means detection/LLM/VLM contend one-at-a-time (this contention is WHY vision was originally kept off the NPU) — schedule them and keep the VLM event-gated. Small-model quality (1.5-2B) is below cloud 70B/11B-vision. Detection is validated on 10H; pose/seg/OBB are not. · depends: Phase 4 (HailoRT 5.2.0 for detection/Qwen2-VL HEFs, 5.3.0 for Qwen3-VL)._

- Export a YOLO11n/YOLOv8 detection HEF (Ultralytics >=8.4.97, format=hailo name=hailo10h, INT8, >=1024 calibration images); port hailo_detector.py _init/_detect/_postprocess from the 4.x sync API to the 5.x ASYNC API + NMS-embedded layout; set enable_hailo:true; schedule against hailo-ollama's single NPU context (one model resident at a time).
- Move hailo-ollama to Qwen2.5-1.5B (offline LLM) and Qwen2-VL-2B / Qwen3-VL-2B (offline VLM), keeping CPU ollama + Moondream Photon as backstops.
- Move face detect/recognize to a Hailo SCRFD/RetinaFace + ArcFace HEF for aligned crops off the CPU.
- (Optional) Hailo CLIP/SigLIP encoder for on-device semantic/visual memory; evaluate Hailo Whisper only as a CPU-offload experiment (keep faster-whisper as the STT workhorse).

**Rollback:** enable_hailo:false instantly reverts to the CPU OpenCV-DNN detector and CPU ollama/Moondream Photon from Phases 1-3 — the on-NPU path is a toggle, not a dependency, so a failure costs performance only, never a capability.

## What NOT to do

- Do NOT make any reliability fix depend on the HailoRT 5.1.1->5.2.0 upgrade — it rebuilds the PCIe kernel driver via DKMS, can break apps pinned to 5.1.1, and is not required for a single offline guarantee. Treat it as optional/late (Phase 4) after the CPU offline stack is proven.
- Do NOT run 'apt install hailo-all' — that is the Raspberry-Pi-OS shortcut and this box is Ubuntu Server 24.04; use Developer-Zone .debs.
- Do NOT close a PyAudio stream from a different thread than the one that opened it — that is exactly what caused the malloc_consolidate SIGABRT crash loop that got the previous mic fix reverted. Bound reads by reopening on the same reader thread, or migrate to a sounddevice callback + bounded queue.
- Do NOT use Picovoice/Porcupine for the wake word — its free tier was discontinued 2026-06-30 (now ~$6k/yr). Do NOT run wake word or TTS on the NPU — no KWS or TTS model exists in the Hailo zoo and dispatch overhead exceeds the trivial CPU cost.
- Do NOT rely on Groq for vision — Llama-3.2-Vision and its Llama-4-Scout replacement are both deprecated. Keep Moondream/NIM for VLM.
- Do NOT put a VLM in the per-frame loop or let a vision call run per frame against NIM's 40 RPM ceiling — fire on demand or on a detector event only, downscale to ~1024px JPEG, and cache.
- Do NOT treat Hailo Whisper as the offline STT workhorse — ~11-12s per 5s chunk with a 5s cap even after upgrade; use faster-whisper base.en.
- Do NOT keep letting the watchdog fix a hang with a full service restart as the primary recovery — it wipes in-memory guard/session state; make in-process recovery the real fix and restart the last resort.
- Do NOT mix embedding vector spaces — vectors from NIM and a local embedder are incomparable; use one embedder per index, set input_type query-vs-passage, and embed the persistent/offline memory locally.
- Do NOT pip-install hailort from PyPI (the erroneous 4.23.0 wheel is the current breakage) — only the matched wheel from the h10-hailort bundle, and only in Phase 4.
- Do NOT edit or trust the stale repo-root /config.yaml (Gonzo, enable_hailo:true) — it is never loaded; the live file is config/config.yaml (Stella, enable_hailo:false). Delete the duplicate to prevent silent mis-edits.
- Do NOT build a sold/commercial product on NVIDIA NIM — its free tier is prototyping/research/personal-use licensed (a home robot is fine); and NIM is cloud-only, so it can never be the offline fallback.
- Do NOT ship any change without a git commit of the working baseline first and a one-line/flag rollback path — the decision log shows well-intentioned fixes repeatedly taking the whole service down.

## Hailo-10H — what it unlocks & the prerequisite

WHAT THE HAILO-10H BUYS FOR FREE (all MIT-licensed; HEFs are free downloads from the Developer Zone free account): it is the entire OFFLINE tier of Stella. There is no "online" Hailo option — it's an on-device NPU that complements the cloud providers. Concretely, once unlocked it runs, entirely offline on the NPU with the Pi CPU freed: (a) real-time vision — YOLOv5→v12 detection (30–130+ FPS on Pi5), SCRFD+ArcFace face detect/recognize (moves face work off the CPU-bound dlib pipeline), Depth-Anything-V2 for navigation, pose/seg/landmarks, PaddleOCR-v5, CLIP/SigLIP zero-shot encoders for a memory index; (b) an offline LLM brain via hailo-ollama (Ollama-compatible REST on :8000) — Qwen2.5-1.5B / DeepSeek-R1-Distill-1.5B at ~7–9 tok/s, TTFT <0.6 s, ~2 W; (c) an offline VLM (Qwen2-VL-2B / Qwen3-VL-2B) for "what am I holding" with no cloud; (d) Whisper ASR (tiny/base/small) on the NPU. THE EXACT PREREQUISITE TO UNLOCK IT: HailoRT is at 5.1.1 on the device; nearly every current 10H HEF (Whisper, VLMs, Llama3.2/Qwen3, PaddleOCR-v5, newest YOLOv11/12) is compiled with DFC 5.2.0+ and throws HAILO_NOT_IMPLEMENTED on 5.1.1 (the mismatch already observed). The version gate is minimum-not-exact: a HEF loads only if its DFC/HailoRT build <= the device runtime. So on 5.1.1 TODAY you already get the v5.1.1+-tagged Gen-AI LLMs (Qwen2/2.5/Coder-1.5B, DeepSeek-distill) and v5.1.x-tagged vision HEFs by pulling the matching model-zoo git tag — but the high-value models need an upgrade. THE UPGRADE: bump the WHOLE stack to one version >= 5.2.0 (target 5.3.0 to also get Qwen3-VL) — all four must match: (1) HailoRT runtime lib, (2) device firmware (bundled in the .deb), (3) PCIe DKMS kernel driver, (4) the Dataflow Compiler used to build any custom HEF. This box is Ubuntu Server 24.04, so the Raspberry-Pi-OS `apt install hailo-all` shortcut does NOT apply — use Developer-Zone .deb packages: install deps (bison flex libelf-dev dkms), remove old h10-hailort* packages, `dpkg -i hailort_5.2.0_arm64.deb hailort-pcie-driver_5.2.0_all.deb hailo_gen_ai_model_zoo_5.2.0_arm64.deb hailo-tappas-core_5.2.0_arm64.deb`, reboot, verify `hailortcli fw-control identify`. Install the matching hailort Python wheel for hailo_platform. Then export detection HEFs with Ultralytics >=8.4.97 `yolo export ... format=hailo name=hailo10h` (INT8, >=1024 calibration images) and drive inference through the HailoRT ASYNC API — the old sync VDevice.configure() itself throws HAILO_NOT_IMPLEMENTED on 10H. RISK NOTE (be honest): the upgrade is invasive — it rebuilds the kernel PCIe driver (DKMS) and can break other Hailo apps or pipelines pinned to 5.1.1; keep HailoRT+firmware+model-zoo tag+DFC on one major line or you re-trigger the version gate. Two things do NOT pay off on the NPU regardless of version: wake word (no KWS model in the zoo; 80 ms-frame dispatch overhead exceeds the trivial CPU cost) and TTS (no Hailo TTS model exists) — keep both on the CPU. And Hailo Whisper is real but currently underwhelming: a field report shows 10H Whisper-base at ~11–12 s per 5 s chunk with a ~5 s audio cap, only ~40% faster than CPU — so it's a CPU-offload experiment, not a latency win; keep faster-whisper as the actual offline STT workhorse.

## NVIDIA NIM plan (existing free key)

FOLD NVIDIA NIM IN AS ONE OpenAI-compatible provider next to Groq/Gemini — the user already holds a working nvapi- key, so this is near-zero effort for three wins on one key + one base URL (https://integrate.api.nvidia.com/v1, Authorization: Bearer nvapi-...). WHICH MODELS, FOR WHAT: (1) LLM reasoning/dialog fallback — nvidia Nemotron-3 (super-120b / lightning-30b) or meta/llama-3.3-70b-instruct, with native tool calling (NVIDIA suggests temp=1.0, top_p=0.95 for tool tasks); use as the SECONDARY online brain behind Groq to catch Groq 429s/outages via an independent network path. (2) Online VLM "what do you see / read this label" — meta/llama-3.2-11b-vision-instruct (the practical free pick; 90b is heavier), with microsoft/phi-3.5-vision-instruct as a same-key alternate model id; pass the frame as an image_url data URI (base64 JPEG, JPG/PNG), reusing the exact same OpenAI client — just switch model id and add the image content block. Downscale frames to ~1024px + JPEG-compress to cut latency and credit burn. (3) RAG/memory embeddings — nvidia/llama-3.2-nv-embedqa-1b-v2 on /v1/embeddings (8192-token context, Matryoshka dims); CRITICAL: set input_type query vs passage (or the -query/-passage model-name suffix) — index docs as passage, embed searches as query, and never mix vector spaces across embedders in one index. FREE LIMITS (honest): free NVIDIA Developer Program key, NO credit card; default 40 RPM (request-upgradeable to ~200 RPM); ~1,000 starter inference credits (up to ~5,000 with a business email); NVIDIA-branded models reported effectively free for prototyping, third-party models draw on credits — verify remaining quota in your own Build console since NVIDIA publishes no single fixed number and versions model IDs frequently. LICENSE (important): the free tier is licensed for prototyping/research/development/testing/personal use ONLY, not commercial production/serving end-users (production = NVIDIA AI Enterprise ~$4,500/GPU/yr) — a personal home robot is squarely inside the allowed use; do not build a sold product on it. HARD CONSTRAINT: everything NIM is CLOUD-ONLY — NIM containers need an NVIDIA CUDA GPU and cannot self-host on the Pi5 or Hailo, so NIM is strictly an ONLINE path with NO NVIDIA offline fallback; the offline path stays the Hailo/local stack. SPEECH is a separate, heavier path: Canary-1b/Parakeet ASR and Magpie TTS (female voice "Aria") are hosted but via NVIDIA Riva gRPC (grpc.nvcf.nvidia.com:443, nvidia-riva-client SDK, per-model function-id + Bearer key), NOT the REST endpoint — add only if you want better online voice; it's medium effort and redundant with Groq Whisper / Gemini TTS for everyday English. ROUTING: prefer NIM when online and under 40 RPM; on timeout/429/401 fail over automatically to the local stack, and throttle/cache vision so a per-frame loop never hits the RPM ceiling.

## Top problems found in the audit

- **[high]** Blocking PortAudio stream.read() in capture_utterance can hang forever if the flaky USB command mic stops delivering frames; the conversation loop never returns, the wake mic stays paused, and Stella goes fully deaf until the hardware watchdog does a full SERVICE RESTART (wiping in-memory guard/session state). The safe reader-thread fix was reverted because cross-thread stream close caused heap corruption (malloc_consolidate SIGABRT crash loop).
  - _fix:_ Per-read timeout via reopening a fresh PyAudio stream on the SAME reader thread (never close cross-thread); or migrate capture to a callback/sounddevice model with a bounded queue. Only true in-process recovery closes this.
- **[high]** Object recognition is completely non-functional (no model file; NPU path gated off and SDK broken). Advertised capability is dead; not even the CPU OpenCV-DNN fallback runs.
  - _fix:_ Lowest effort: drop data/models/yolov8n.onnx (CPU, no config change). NPU: reinstall HailoRT-5.1.1 pyhailort wheel, enable_hailo:true, add 5.1.x-DFC HAILO10H yolov8n.hef, port _init_hailo/_detect_hailo/_postprocess to 5.x + NMS-embedded layout.
- **[high]** Online/offline capability cliff for the LLM: when Groq+Gemini are down/rate-limited, the chain falls to the Hailo NPU which is NOT tool-capable AND web/weather pre-injection was already skipped (gated on a cloud client merely existing). Device control, reminders, music, photos, guard, gestures and all web-grounded answers silently stop working offline while keyword handlers keep going.
  - _fix:_ Gate web pre-injection on whether a cloud client actually ANSWERED, not on existence; add a text-based tool-call shim for the Hailo/qwen backend (_TEXT_TOOLCALL_RE already recovers text tool calls) so a subset of tools works offline.
- **[high]** Wake-word 'Stella' is inherently fragile: Vosk small-EN never transcribes 'stella' (renders settler/taylor/stellar/sella...); detection rests on a hand-maintained alias set + 'stel' prefix + Levenshtein<=2. New mis-renderings are missed wakes; aliases (taylor/sailor/settler/stellar) invite false wakes on normal speech.
  - _fix:_ Replace the string-matching patch with a trained keyword model: openWakeWord (CPU) or Porcupine (pvporcupine not installed), or a Hailo wake-word .hef. A proper-noun wake word needs a trained detector, not a general ASR + alias list.
- **[high]** Master-authorization is bypassable. The deterministic keyword handlers (_maybe_ac, _maybe_music, _maybe_mirror, _maybe_face, guard ARMING) run FIRST and short-circuit before think(), and perform NO master check — while the equivalent LLM tools (set_ac/control_device/set_guard_mode) DO enforce master_mode. Any present speaker (even 'unknown, no recent face') can control AC/music/screen/hand and ARM guard by phrasing it as a keyword command.
  - _fix:_ Single source of truth for auth: enforce the same master gate inside every keyword handler (or route all capability calls through one dispatch layer that checks auth once). Also unify _do_device_control vs control_device _remote_master handling.
- **[high]** Microphone enumeration flip-flop: PortAudio only lists ALSA capture devices free at probe time; if the camera wake mic ('Auto Focus Camera') isn't free at startup, by-name resolution returns None and PyAudio opens 'default' (pulse) whose ONLY source is the USB command mic — collapsing both roles onto one mic. Self-heals on later reopen but with no guarantee and silently.
  - _fix:_ Pin mics by stable ALSA hw: identifier (card by USB path) instead of PortAudio name; fail loud (log ERROR + retry) when the wake mic resolves to None rather than silently opening 'default'. Wire the unused AudioManager exclusive-lease API.
- **[high]** venv Hailo Python bindings are entirely non-functional (pip hailort 4.23.0 vs system HailoRT 5.1.1 firmware/runtime) — a client/firmware major mismatch. All on-NPU vision code is dead; the erroneous wheel violates requirements.txt guidance.
  - _fix:_ pip uninstall hailort; install the HailoRT-5.1.1 aarch64/cp312 pyhailort wheel from the h10-hailort SDK bundle (not PyPI). Then evaluate NPU vision vs single-context contention with hailo-ollama LLM.
- **[medium]** Secret hygiene: the review snapshot contains real, live plaintext credentials — .env (GROQ/GEMINI/MOONDREAM/TELEGRAM/SENSIBO), tinytuya.json (Tuya cloud apiKey+apiSecret), devices.json (Tuya local key). Working keys, not placeholders.
  - _fix:_ Rotate all exposed keys; ensure .env/tinytuya.json/devices.json are gitignored and never in review copies; move secrets to a secrets store or systemd EnvironmentFile with 600 perms.
- **[medium]** Watchdog can hard-restart the service mid-conversation. Threshold is 60s in code (docs say 120s), and _conv_activity is stamped ONLY when Stella speaks or at session start — not on user speech or during slow cloud-LLM turns — so a long user pause or a ~20s NPU/slow-provider round-trip can trip a full `sudo systemctl restart airobot`.
  - _fix:_ Stamp _conv_activity on user speech and on LLM request start/finish; raise threshold to the documented 120s; prefer in-process session-abort over full service restart.
- **[medium]** Face recognition is unreliable: master recognized with wide borderline similarity (0.40-0.75) interleaved with 'Unknown sim=0.00'. Root cause is Haar-cascade boxes fed directly to dlib without alignment (face_backend='opencv'), plus 'similarity'=1.0-euclidean_distance is a mislabeled metric that never approaches 1.0, and no DeepFace fallback is installed. Double frame-skip (camera frame_skip=8 x module frame_skip=8) processes ~1 in 64 frames (~0.47 fps).
  - _fix:_ Switch face_backend to dlib HOG / SSD / SCRFD (or a Hailo RetinaFace .hef) for aligned crops; report raw distance not '1-distance'; remove the double frame-skip.
- **[medium]** requirements.txt is stale/incomplete: a clean `pip install -r requirements.txt` would silently disable live features. It omits paho-mqtt, tinytuya, mediapipe, opencv-contrib-python, yt-dlp (all installed AND used, all loaded in try/except so they vanish without crashing). Still titled 'Gonzo'; no pins/lockfile (114 installed vs ~23 declared).
  - _fix:_ Regenerate a pinned requirements.txt / lockfile from the working venv (excluding the system-provided hailort); update check_deps.py to audit the real keys/deps.
- **[medium]** Reasoning-model token budget risk: live groq_model gpt-oss-120b / gpt-oss-20b are reasoning models but requests pass max_tokens=512 which Groq counts as max_completion_tokens INCLUDING reasoning tokens — complex answers risk truncation (finish_reason=length) or empty content that silently falls to the next provider. No <think>/analysis stripping safety net.
  - _fix:_ Raise max_tokens for reasoning models, set reasoning_format=parsed/hidden, and extend _strip_tool_tags to drop inlined <think>/analysis if it ever leaks.
- **[medium]** Two competing config.yaml files and other dead/duplicate code invite silent mis-edits. Repo-root /config.yaml (Gonzo, enable_hailo:true) is present on repo AND Pi but NEVER loaded (loader uses config/config.yaml); its header says 'the ONE file you edit'. Also duplicate settings.py/manager.py/wake_word.py copies and unreachable legacy paths (openai-whisper, single-backend/escalation methods).
  - _fix:_ Delete the legacy root config.yaml and duplicate/dead modules; keep a single loaded config with a header pointing to itself.
