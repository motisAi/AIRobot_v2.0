# Stella — Architecture v2: Layout, Self-Evolution, Safety Net (2026-09-19)

_Supersedes the folder-layout and process parts of [stella-architecture-2026-09-13.md](stella-architecture-2026-09-13.md). The capability stack (online primary → offline fallback per capability), the Hailo/NIM plan and the phased roadmap in that document stay valid and are referenced here, not repeated._

## 1. What this version adds

| Goal (Moti, 2026-09-19) | Design answer |
|---|---|
| Code organized and easy to understand; every physical part has its own class in its own file | **`parts_used/`** — one file per part (camera, mics/speaker, Hailo NPU, ESP32 hand, microcontroller bridge, 4G modem, WiFi, RC toy). Everything else grouped by *what it does* (`modules/<capability>/`). Stale duplicates deleted. |
| One main README, linking to focused READMEs | `README.md` at the root is the map. Each top-level folder with >3 files gets its own `README.md`. Docs live in `docs/`. |
| Never fix the same bug twice | **`bug_report/`** — `bug_NNN_<slug>.md` per bug, fixed template (symptom → root cause → fix → verify → will it recur). Seeded from the whole project history. Rule: **no fix is committed without its bug file.** |
| Stella should be "the smartest she can, fastest she can, as much self/machine learning as possible" | **`evolution/`** — self-knowledge (manifest), a deterministic **Guardian** (health + smoke test + auto-rollback), a **Scout** that looks for upgrades and *reports* them, and a **morning report** on Telegram. Free models only. Autonomous merging is explicitly *not* in v2 (see §5). |
| Cheap RC toy soon | `parts_used/rc_toy.py` + `rc_toy.connected: false` in config; a `RCToy` class with a no-op backend today and pluggable transports (BLE / WiFi / ESP32 relay). |
| Rollback must always be trivial | Every step is its own commit, pushed before the next. `deploy/deploy.sh` = restart → Guardian → on failure `git reset --hard <previous>` + restart. |

**Rules that keep it organized**
1. A file in `parts_used/` wraps exactly one kind of physical part and exposes `start() / stop()` plus `is_available()`; no business logic (no "greet when face seen" there).
2. `modules/<x>/` never talk to hardware directly; they go through a `parts_used` class handed to them by `main.py`.
3. `core/` knows nothing about hardware or the cloud.
4. Root level holds only `main.py`, `README.md`, `requirements.txt`, `stella_manifest.yaml`. Operator scripts live in `tools/`.
5. Runtime paths stay relative to the repo root (`data/...`); `WorkingDirectory` in the unit file guarantees that.

## 3. Migration procedure (mechanical, reversible)

Verified before writing this: **no dynamic imports** (`importlib`/`__import__`) except `check_deps.py`, **no module paths in YAML/shell/HTML**, and all `sys.path` hacks point at the repo root, so a rename + import rewrite is complete.

1. `git mv` each file to its new place (history preserved).
2. Rewrite imports with an exact old→new table (sed on `from modules.hardware.camera_manager import` → `from parts_used.camera_usb import`, etc.). `from modules.hardware import wifi` → `from parts_used import wifi_adapter as wifi`.
3. Delete stale copies: tracked `modules/vision/wake_word.py` (an old duplicate of `modules/audio/wake_word.py`); untracked/ignored root copies `robot_brain.py settings.py text_to_speech.py manager.py telegram_bridge.py _patch_objfix.py`. They are all in the 2026-09-13 tarball backup on the PC.
4. `python -m compileall` + `tests/test_imports.py` (imports every module the way `main.py` does) on the Pi.
5. `deploy/deploy.sh` → restart → Guardian must pass → commit → push.
6. Rollback at any point: `git reset --hard <commit before the move>` and restart. Nothing outside the repo changes.

## 4. Guardian — the safety net everything else stands on

Deterministic, no LLM, runs in <30 s, exit 0/1, writes `evolution/reports/guardian-latest.json`.

| Check | Pass condition |
|---|---|
| syntax | `compileall` over the repo (venv excluded) |
| imports | every module `main.py` imports loads under the venv |
| config | `config/config.yaml` parses and `RobotConfig` builds |
| service | `systemctl is-active airobot` within 90 s of restart and stays up 60 s (no restart loop) |
| log health | last 2 min of `journalctl -u airobot` contains ≤ N ERROR lines and none of the known-fatal patterns (`Traceback`, `malloc_consolidate`, `HAILO_OUT_OF_PHYSICAL_DEVICES`) |
| hardware (soft) | reports camera nodes, capture PCMs, `/dev/hailo0`, serial ports — informational unless the config says the part must exist |
| brain | hailo-ollama answers `/v1/chat/completions` in < 30 s (soft when offline is not required) |
| resources | disk ≥ 2 GB free, RAM ≥ 500 MB available, `vcgencmd get_throttled` == 0x0 (undervoltage is reported loudly) |

`deploy/deploy.sh [<commit>]`: records `HEAD`, restarts, runs Guardian; on failure resets to the recorded commit, restarts, and sends a Telegram line. This is also what Claude uses for every deployment from now on.

## 5. Self-evolution — what is in v2 and what is deliberately not

From the phone blueprint (Scout / Lab / Guardian / Builder), v2 builds the parts that add knowledge and safety, and holds back the parts that would let a small model change a running robot unsupervised:

| Blueprint piece | v2 decision | Why |
|---|---|---|
| Manifest (`stella_manifest.yaml`) | **Build.** Generated, not hand-written: hardware nodes, models in `data/models`, providers with keys present, services, capabilities from config flags, known weaknesses from `bug_report/` marked `recurring`. | Stella's self-knowledge; also what Scout and the morning report read. |
| Guardian | **Build first** (§4). | Protects the reorganization and every future change, human or machine. |
| Scout | **Build, report-only.** Daily 03:00 timer: `pip index versions` for pinned AI packages, GitHub release tags for Piper/Vosk/openWakeWord/faster-whisper/Ultralytics, Hailo model-zoo tag. Free LLM scores relevance 1–10 against the manifest. Writes to `evolution.db`, never installs. | Finds improvements without touching the system. |
| LLM client | **Build.** Order: hailo-ollama (local, free) → Groq → Gemini. Never Claude/OpenAI (boss rule, blueprint rule). Every call logged with purpose and token counts. | Cost visibility; offline-first. |
| Morning report | **Build.** `reports/YYYY-MM-DD.md` + a 5-line Telegram summary: Guardian status, throttling events, error count, Scout findings, open recurring bugs. | Moti sees Stella's state and ideas daily without asking. |
| Lab (sandbox testing) | **Defer** to v3. | Needs a second venv and test data; the Pi is already at its limit while running vision + speech + LLM. |
| Builder (auto-merge) | **Defer**, and gate behind `evolution.require_operator_approval: true` when it arrives. | A working Stella beats a newer broken one. Approval by Telegram reply is the intended UX. |
| Hardware inbox (YAML → generated integration code) | **Defer**, but the `parts_used/` contract (start/stop/is_available) is designed so generated code has a fixed shape to follow. | |
| "Pause when operator is active" | **Build** into the timer: skip if an SSH session is open (`who`) or the git tree is dirty. | Never fight Claude Code over the repo. |

Resource rule: Scout and report run under `nice -n 15`, only when CPU < 60 % and ≥ 2 GB disk free.

## 6. RC toy contract

```yaml
rc_toy:
  connected: false        # flip when a toy is wired
  transport: "null"       # null | esp32_serial | ble | wifi_http
  port: "/dev/ttyUSB1"
  address: ""             # BLE MAC or http://ip
  max_speed: 0.5          # 0..1 safety cap
  deadman_seconds: 2.0    # stop if no command for this long
```
`RCToy` exposes `drive(forward, turn)`, `stop()`, `is_available()`. Voice/LLM tool `control_toy` only appears when `connected` is true; every drive command is master-gated and dead-manned. Transport implementations are added as small classes in the same file.
